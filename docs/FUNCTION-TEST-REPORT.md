1. **侧边栏「编辑」「删除」两个按钮 100% 不可用** —— 点一下就抛

应该维持一个已经不存在的坏状态。红改绿不是放水，是把判据掰回它该量的东西。

### 一之三、**没有**改、也不该改的

- **B7 连接闸门「永久锁死」** —— 4 位评审一致判否。复位点虽然只有两处，
  但**两个都在各自函数第一行**，中间没有语句能先抛；`worker()` 的
  `except Exception` 覆盖 paramiko 全部常规异常。有人实测把 `connect` 打成
  必抛 `OSError`，跑完事件循环闸门确实复位。**「没有 `finally`」不等于
  「会锁死」** —— 为它加一个用不到的 `finally`，只会让下一个人以为那里本来
  就有洞。对应判据已改成钉「两个落点都在第一行复位」这条真实不变量。
- **B11 的主体语义** —— OpenSSH 的 `-L` 确实是「关监听不杀已建连接」。
  这一轮选了「停 = 真停」，理由是面板把停掉的规则整行画成没有连接，
  **界面给了承诺内核就得兑现**；取舍写进了 `tunnel.py` 的 docstring。
- **B19 的代码侧** —— 改文档，不动那处 `StandardKey.Close`。

### 一之四、仍然没做的（不在清单里，也不该顺手做）

- `upload` 侧临时件（`posix_rename` 是 SFTP v3 扩展，最小服务端不支持）
- `_TransferWorker` 传 Qt 父对象（要真修得先把它改成 `QObject`，是结构改动）
- macOS / Linux 分支、真机高 DPI、多显示器、Wayland
- 真 SSH 服务器端到端（`tests/_live.py` 需要 `MAVIS_LIVE_*` 环境变量）

## 二、这一轮是怎么做的

### 2.1 流程

```
5 位专家并行盘点全仓功能           → 689 条功能项（带 预期行为 / 代码位置 / 可测性）
        ↓
监理审阅测试计划与口径
        ↓
5 位 worker 按域各写 1 套功能测试   → 1063 条判据（红的不许改软）
        ↓
跑 5 套新测试 + 47 套全量回归      → 72 条红
        ↓
5 位专家独立复核每一条红            → 逐条投票（成立 / 不成立 / 证据不足）
        ↓
≥4/5 票成立才算数；3 轮定不下来的由监理拍板
        ↓
本报告
```

### 2.2 判据口径（这一轮刻意坚持的几条）

1. **判据钉在「用户看得见 / 磁盘上看得见的字节 / 远端收到哪些字节」上。**
   不许用「代码里有没有那个 if」当判据 —— 那是量实现，不是量行为。
2. **红的就是发现，不许改软让它变绿。**
   这一轮的产出是「一份测试结果」，不是「一份全绿的门禁」。复核为真缺陷就保留红；
   复核为「测试自己写错」才修判据，并且要说清错在哪。
3. **关键判据必须有元断言（负向对照）。**
   把被测实现换成缺陷版本，那批断言必须变红。没做元断言的判据可能是恒真的。
4. **探针要先自校验。**
   量像素的扫描器得先在一个「已知有内容」的地方命中一次 —— 扫描说「有」可信，
   说「没有」时要先怀疑扫描器。
5. **异步一律事件驱动**，不许固定 `sleep`。
6. **不许碰用户真实配置。** `AppSettings` 必须指走 `_path`；`SessionStore` 必须
   **两个参数都给**（第二个 `config_dir` 才是密钥目录，漏传会读用户真实的
   `secret.key` —— 本轮有人踩过）。

### 2.3 退出码语义（沿用仓库既有约定）

| 退出码 | 含义 |
|---|---|
| 0 | 全部通过 |
| 1 | 至少一条判据红 |
| 2 | 一条没红，但有判据因前提不成立而没评上 —— **单列成一类，不许混进「通过」** |

第 2 类单列的理由：这个仓评审实测过「只坏焦点」和「焦点坏 + Esc 逻辑也真坏」
两种情况输出完全一样，而退出码只看 FAIL，于是真回归被静默跳过、整套还报成功。

### 5.1 评审方法

29 条发现项交给 **5 位独立评审**，各自从不同视角取证、互不可见：

| 编号 | 视角 | 任务 | 票是否有效 |
|---|---|---|---|
| R2 | 证伪优先 | 专职推翻，用五把尺子量（测试写错 / 判据恒真 / 前提不成立 / 代码不可达 / 后果不可达） | ✅ |
| R3 | 后果与严重性 | 只回答「用户看到什么」，敢于下调 | ✅ |
| R4 | 契约与文档一致性 | 额外扫文档漂移 | ✅ |
| R5 | 判据可信度 | 审计 1063 条判据里有没有恒真项与虚假绿灯 | ⚠️ **超时终止，零输出** |
| R1 | —— | 首轮第 1 票 | ❌ **票表被截断，不可用** |
| R1' | 最短路径复核 | 专攻票型分裂项，替代 R1 | ✅ |

**投票口径**：`≥4/5 票成立` 才算数；最多 3 轮；3 轮定不下来的由监理拍板。
因 R1 票丢失，实际按 **4 张有效票、≥3/4** 判同一件事（见 5.2 的说明）。

**过程记录**：最初派出的第 1 票在返回时最终投票表被截断，只剩过程日志，

### 5.3 定稿：确认成立且必须修（按严重性）

#### 高

**1. A5 —— 侧边栏「编辑」「删除」一点就抛异常，这两个按钮 100% 不可用**
`main_window.py:1571` / `:1573` 把两个 `QPushButton` 的 `clicked` **直接连**到
`_on_edit_session` / `_on_delete_session`，没包 lambda。PyQt6 的 `clicked(bool)`
恒传 `False`，而 `:2036` / `:2049` 的 `item is not None` 对 `False` 判真 →
`_session_of(False)` → `False.data(...)` → `AttributeError`。
右键菜单里的同名项走 lambda 传 `item`，所以正常 —— 也就是说不止一个入口坏了。
**后果（经 5 位评审实测，含我自己独立复核）**：
- 不装崩溃守卫：进程 abort，退出码 `0xC0000409`
- 装了（本仓库 `main.py:109` 必装）：弹一次「发生错误」框，**关掉后进程正常存活**、
  窗口和其它标签不受影响，但这两个按钮永久不可用
- 所以「崩进程」只在绕过 `main.py` 时成立；出货路径的真实后果是**功能永久失效**

**2. B3 —— 滚回历史后拖选复制，剪贴板里是一串列号控制字符**
绘制路径（`terminal_widget.py:1079-1084`）已改用 `raw.values()` 取 `Char.data`，
并写了长注释解释 pyte 0.8 的 `history.top` 是 `StaticDefaultDict`；
**复制路径 `selected_text()`（`:1236-1240`）还是 `for b in raw: chr(b)`** ——
迭代映射给出的是列号 0,1,2…。实测 `'HISTMARK7'` 被复制成 `'\x00\x01\x02\x03\x04\x05\x06\x07\x08    '`。
这是典型的**修 A 漏 B**：同一个坑在绘制侧修过，复制侧没跟上。
我已独立读源码复核确认两条路径确实不一致。

**3. B9 —— 复制一次之后，Ctrl+C 再也发不出 SIGINT**
`copy_selection()`（`:1256-1260`）只写剪贴板、不清选区锚点，而 Ctrl+C 分支
（`:867-872`）只以 `has_selection()` 为闸门。复制一次后在下一次点击之前，
Ctrl+C 全是静默重拷，`0x03` 发不出去。README 承诺「只有确实存在选区时才会被
复制行为吃掉」—— 选区永不消失，这条承诺实际不成立。

**4. B2 —— 会话级传输状态条被文件面板「收编」，终端页看不到 ZMODEM 进度**
`main_window.py:321` 把状态条加进 SessionTab 的 `strip_row`（`outer` 布局里，
位于 `sub_tabs` 下方）；`sftp_panel.py:1262` 取的是**同一个** widget
（`self.strip = self.ctrl.strip`，`ctrl` 就是 SessionTab 传进来的那个），
`:1268` 又 `root.addWidget(self.strip, 0)` —— `QLayout::addWidget` 会把控件
reparent 到该布局所属窗口。于是**ZMODEM 跑在终端页时，进度条在文件页**，
`strip.isVisibleTo(会话窗口) == False`。
这正是 `main_window.py:300-304` 注释里明写「绝不能发生」的事。

**5. B11 —— 停止一条转发规则后，它已建立的连接继续转发**
`Forward.stop()`（`tunnel.py:405-412`）只关监听 socket 并 join **accept 线程**；
`_serve`（`:453`）与两个 `_pump`（`:239`）都不看 `_stop`，已 accept 的 socket 也没被关。
`stop()` 里**没有任何跟踪已建立连接的字段**。界面上还看不出来 ——
面板对关闭的行把连接数列硬写成「—」。用户以为关掉了转发，其实数据还在跑。

**6. A3 —— 编辑会话时切换认证页签，原口令被清空**
`connect_dialog.result_dict()`（`:331-343`）以**当前页签**为唯一判据写凭据，
另一套直接写空串；`main_window.py:2044` 用它整条重建会话。
触发方向有两位评审给了不同读法，但两条都指向同一个根因：
- 密码会话误点「SSH 私钥」页签 → `password=''`、`auth_method='key'`
- key 会话随手点一下「密码」页签 → `key_filename`/`key_passphrase` 变空
其中一条被 `accept()` 的必填校验拦下、只弹提示，另一条**没有**任何拦截，
`upsert` 落盘即不可逆、零提示。**根因是同一个：无提示地清空用户没打算改的凭据。**

**7. A1 —— 一次越界值，用户从此再也存不进任何设置**
`settings.py:341` 把「被夹住」的值写进 `load_error`，而 `save()`（`:414`）
只看 `load_error` 非空就拒写。越界值留在文件里 → 下次 `load_from` 再次置
`load_error` → **重启也不能自愈**。界面控件的量程全部落在 core 量程内，
所以触发条件是手改配置文件或旧版本遗留。
有评审实测：点「确定」瞬间状态栏就有 6 秒提示、关窗口另有模态框，
所以「用户完全不知情」不成立；但「改任何设置都无效」成立。

**8. A2 —— 加密不可用时，`sessions.json` 静默落明文口令**
`settings.py:203-209` 在 `CryptoUnavailable` 时退回 `json.dumps` 明文，
`encrypted=False`、`load_error` 仍为空，`upsert()` 照常返回。
**触发条件比最初报告窄**：需要「磁盘上没有 `sessions.json`」+「`secret.key` 是
0 字节或垃圾」同时成立；最常见的「密钥丢失」场景实测**不落明文**（走
`_writable=False` 拒写、文件原样保留）。但 README 承诺的「逐字段加密」在这条
路径上当场失效，且 `SessionStore` 上**没有任何字段能读到这次降级**。

**9. A4 —— 会话文件出问题时，界面上没有任何出口**
`sshclient/ui/` 下无一处读 `store.load_error`（`main_window.py:2179` 只读
`AppSettings.load_error`）。密钥不匹配 → 侧栏静默变空、改任何会话都不落盘，
用户无从判断是文件没了还是自己被挡了。
另一半也成立：`_quarantine`（`:183-191`）隔离坏文件后**不**置 `_writable=False`，
下一次 `upsert` 会用残列表覆盖原路径 —— 同一函数的另两个分支（密钥不匹配）是置了的，
**一函数两策略**。

**10. B6 —— `open_shell` 失败留下死标签 + 泄漏一个 `SSHConnection`**
标签在 `main_window.py:2103` 已经 `addTab` 进标签栏、`self._conn` 已赋值，
然后 `attach()`（`:491-495`）才提前 `return` —— conn 永不 `close()`。
点「重新连接」会**再开一个新标签**，死标签不消失。

**B7「连接闸门 `_connect_inflight` 会永久锁死」—— 不成立（3/4 有效票判否）**

这一条是 `_fwin.py` 报出来的，当时列的理由是「`open_session` 没有 `finally`、
没有看门狗，复位只在成功/失败两个落点」。4 位评审独立核到同一个结论：
**两个落点都在各自函数的第���行**（`_on_connect_ok` 的 `:2093`、

### 5.6 监理裁定的三处分歧

有三处 5 票没有一致（4:1），按流程由监理拍板。三处我都自己读了源码/跑了复核：

**分歧一：B2「状态条被收编」—— 裁定成立**

一位评审判**不成立**，理由是「条子加在 SessionTab 顶层 `outer`、位于 `sub_tabs`
下方，未 reparent 进 SftpPanel」。这半句描述对 SessionTab 侧成立，但**漏了
SftpPanel 侧**。`sftp_panel.py:1262` 的 `self.strip` 就是 `main_window.py:306`
那个 `self.transfer_ctrl.strip`（同一个对象，`ctrl` 由 `main_window.py:523-525`
注入），`:1268` 对它 `root.addWidget` —— `QLayout::addWidget` 会把控件 reparent
到该布局所属窗口。三位评审的运行时实测（`strip.parent()` 从 SessionTab 变成
SftpPanel）与之相符。
**裁定：成立。** 一位评审读了代码的一半就下结论，这是**漏读**而不是分歧。

**分歧二：B4「连上后不主动同步 PTY 尺寸」—— 裁定成立，但范围收窄**

判不成立的理由是「新标签 layout 必然触发一次真实同步」。这个理由**有道理**：
实测那位评审测出 0 次 `resize_pty`，是因为它的装置里终端始终停在构造尺寸
（网格 80×24），而 `_recompute_grid`（`:590-591`）在网格未变时提前 return ——

**分歧三：B25「`encrypted` 恒 False」—— 裁定成立**

判不成立的理由是「`encrypted` 维护得很正确：`:202` 置 True、`:209` 置 False、

### 仍然没做的

- **【本轮新确认，比原来那条更重】黑洞型断网会让整个 SFTP 面板哑到会话结束。**
  评审实测：真 TCP 黑洞（accept 后不回应也不关闭）**70.0 秒零异常、仍卡在
  `recv`**；对照组对端主动关闭 0.00 秒就 FIN。`upload()` 主体的
  `with self._held()` 是**无上限**的（设计如此：传输必须拿到锁），而
  `sftp_client._read_response` 没有任何超时，所以 `put` 吊住 → 那把锁永不放 →
  `listdir` / 远程面板刷新 / 上传 / 下载全部不响应。
  **原注释写的「`set_keepalive(20)` 通常让它在分钟级自愈」是错的**：paramiko 的
  keepalive 是 `global_request("keepalive@lag.net", wait=False)`，**只写包、从不
  读包、不等响应**，对「丢包不回 RST」完全无效。上界由 TCP 重传策略与对端是否
  发 FIN 决定，**应用层给不出有限秒**。
  用户侧无自救出口：状态条停在 running、点「取消」只置标志不打断已发出的那一个
  （`transfer_controller` 全文无 timeout / watchdog）、`_set_busy(True)` 禁用的
  按钮只有 `_on_transfer_done` 会放开而它永远不来 —— 只能手动断开重连。
  **要治它得在 `_TransferWorker` / `SftpTransfer` 上加整体看门狗**，那是另一个
  改动，本轮没混进来。
- **`_swap_in_place` 里「删旧再改名」那一步的 `remove` 仍无上限**
  （`sftp_panel.py` 的 `_swap_in_place`）。评审**实测否决了**「顺手给它加限时」
  这个诱人做法：`_probe` 的工作线程跑在 `with self._held()` 上，而 `RLock` 的
  可重入是**按线程**的 —— 调用线程持锁时探测线程永远抢不到，稳定超时，
  **「删旧再改名」整条退路不执行**（实测 `calls=[]`），不支持 `posix_rename` 的
  服务端上覆盖上传直接报废。保留现状：它紧跟的 `rename` 会因目标仍在而抛，
  异常照样从 `upload` 的 `except` 出来，用户看得见。
- **`_probe` 被放弃的线程仍会占着通道锁**：那条探测在飞期间，所有无超时
  `_held()` 的路径（`listdir`、远程面板刷新、`upload`/`download`）无限期阻塞，
  同时 `_probe` 变成 **0 毫秒瞬时**拒答。第二个症状 docstring 原本完全没写。
  这是设计取舍（paramiko 没有「取消一次正在等的 stat」的办法），本轮只补了文档。
- macOS / Linux 分支、真机高 DPI、多显示器、Wayland、真 SSH 服务器端到端
  （`tests/_live.py` 需 `MAVIS_LIVE_*` 环境变量）。

- **上传失败后的远端清理没有上限**（原「仍然没做的」第一条）。走 **5 位专家
  独立评审**（修法 / 证伪优先 / 后果与代价 / 最小改动与回归面 / 边界与不变量），

### 8.2 评审探针写到了用户真实配置

`%APPDATA%\MavisSSH\settings.json` 在 **12:34:48** 被重写，

- 仓库自带的 `tests/_readme.py` 守卫只扫 `tests/` 下的脚本，**管不到临时探针**

例如在 `AppSettings.save()` 里对「`_path` 为空且不是 `load()` 来的」直接拒绝落盘。
